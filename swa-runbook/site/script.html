SLIDES 1–3 · DECKOPENING

Test the boundary.

READ ALOUD · SLIDE 1
“Red teaming is a controlled attempt to make an AI system cross a boundary it should respect. Today I’ll show how we launch a test, inspect real findings in Microsoft Foundry, and use evidence to decide what needs fixing. I’ll also show two deliberately seeded failures in an isolated All Clear demonstration. Those seeded cases are not vulnerabilities discovered in the production application.”
READ ALOUD · SLIDE 2
“Ordinary testing asks whether the system can do its job. Red teaming asks whether someone can steer it outside that job—toward information it should not reveal, instructions it should not follow, or actions it should not take. We are testing behavior at boundaries, not merely checking whether an answer sounds confident.”
READ ALOUD · SLIDE 3
“All Clear is running in my CLI environment, and I’ve tested it extensively. That is useful history, not a guarantee that we have exhausted every failure mode. A correct answer on a normal request does not prove that the same system will preserve its access controls and evidence boundaries under adversarial input.”

DECK: Explain the contrast; do not represent prior testing as complete security coverage.

SLIDE 4 · DECK / PRIVATE ADAPTER EVIDENCEBASELINE

Preserve useful behavior.

READ ALOUD
“All Clear’s legitimate job is incident triage: many incoming signals become a clearer operational response. The baseline we want is expected routing, permitted knowledge retrieval, and a situation report faithful to trusted incident information. A system that refuses every request is not a useful incident-triage system. Today’s focused checks do not establish a full-application baseline.”

SLIDES 5–6 · DECKAUTHORITY

READ ALOUD · SLIDE 5
“The documented All Clear flow starts with classification, then deterministic routing, followed by bounded actions such as incident creation, knowledge search and sitrep generation. READ ALOUD · SLIDE 6
“A model or prompt-agent result tells us about that tested surface. An application test can tell us about a retrieval or state boundary. A Foundry evaluation scores outcomes for its configured target and criteria. Deterministic assertions give us repeatable, specific checks. They complement each other; they are not interchangeable. Let’s start a new run, then inspect completed evidence while it processes.”
